# ADR-S02: Introduce `Kun.Sandbox` Module — E2B-compatible sandbox abstraction for Kun consumers

**Status**: Accepted
**Date**: 2026-04-23
**Author**: claude-kun (Kun framework specialist)
**Related specs**:
- `NeuroAgent_Sandbox_Spec_v1.1.md` §2 / §4 / §14 (E2B-compatible surface)
- `ADR-S01-E2B-compatible-API.md` (Supervisor REST API adopts E2B v2 shape)

---

## 1. Context

NeuroAgent is building a self-hosted Sandbox Supervisor that exposes an
E2B-compatible REST API (see ADR-S01). The *Python* harness
(`neuroagent-python`) will drive that Supervisor through an E2B-style
SDK. But sandbox usage is not a Python-only concern: the **C# business
services** in `neuroagent-csharp` have first-class "run this code / run
this command / produce these files" scenarios that today are pushed up
to the Python harness even when the business logic lives in .NET:

- **Platform: data preprocessing** — ingest + transform uploaded CSV/XLSX
  into normalised parquet/JSON before handing to analysts.
- **Edge: document render** — run `weasyprint` / `pandoc` to convert
  reports generated by C# business logic.
- **Platform: lightweight one-off scripts** — tenant-supplied validation
  rules or transform functions that must execute in isolation.
- **Notification: chart render** — headless Chromium to turn a
  dashboard snapshot into a PNG attached to an email.

These flows currently have three bad options:

1. **Round-trip through the Python harness** — the C# service calls the
   Python agent service just to borrow a sandbox. Extra hop, extra auth
   surface, harness tooling is agent-centric not service-centric.
2. **Each .NET service reinvents a Supervisor HTTP client** — drift,
   duplicated auth / retry / tracing logic, each service has to learn
   the E2B v2 schema from scratch.
3. **Run code directly in the service process** — unacceptable: no
   isolation, no egress control, no tenant-scoped audit.

The framework layer is the correct place to unify this. Kun already
owns other horizontal infrastructures consumers rely on
(`Kun.EventBus`, `Kun.Storage`, `Kun.Identity`, …); sandbox execution
is the same category: an abstraction with pluggable backends and a
stable surface.

At the same time, ADR-S01 established **E2B v2 as the canonical REST
shape** for the Supervisor. The .NET abstraction should mirror that
shape exactly so that (a) the code reads the same as the Python SDK,
(b) future migration to E2B Cloud is equally cheap for .NET consumers,
and (c) nothing in `Kun.Sandbox` becomes a competing abstraction
relative to the Supervisor spec.

## 2. Problem

Provide a .NET-idiomatic sandbox abstraction that:

1. Lets any C# service in `neuroagent-csharp` (or a future Kun consumer)
   create sandboxes, run processes, read/write files, and kill
   sandboxes — without knowing whether the backend is a local stub, the
   self-hosted Supervisor, or E2B Cloud.
2. Aligns the interface contract 1-to-1 with the E2B v2 API shape
   (endpoints, fields, camelCase JSON), so consumers who already learned
   the Python SDK can read .NET call sites unchanged.
3. Preserves Kun's AOT / zero-reflection posture — callable from
   `Kun.Gateway`, `Kun.AspNetCore`, or any AOT-strict service.
4. Does **not** ship a runtime. The runtime lives in
   `neuroagent-python/sandbox_supervisor` (Python, per Spec v1.1 §14).
   `Kun.Sandbox` is abstraction + client.

## 3. Decision Drivers

- **D1 — consumer parity**: C# services must have the same sandbox
  ergonomics the Python harness already enjoys. Today they don't.
- **D2 — no drift from the Supervisor spec**: every divergence between
  the .NET contract and the Supervisor REST contract is a future bug.
- **D3 — E2B Cloud path preserved**: if Mode D (ADR-S01 §14.4) is ever
  adopted, .NET consumers should migrate by flipping a registration
  line, not by rewriting call sites.
- **D4 — AOT strict**: .NET services in this repo publish AOT.
  Sandbox client code must not introduce runtime reflection.
- **D5 — testability**: unit tests for business code that calls a
  sandbox must not require Docker; an in-memory provider must exist.

## 4. Options Considered

### Option 1 — No Kun module; each C# service writes its own Supervisor client
**Rejected.** Directly violates D1 / D2. Guarantees drift. Every
consumer re-learns the E2B schema.

### Option 2 — Kun hosts the *runtime* (port the Python Supervisor into .NET)
**Rejected.** The Supervisor runtime is deliberately owned by
`neuroagent-python` because it manages Docker / gVisor / Envoy /
Browser CDP proxying — all concerns where the Python ecosystem is
stronger and the team's existing ops playbook is already invested.
Re-implementing in .NET gives no consumer value, doubles the operational
surface, and violates Spec v1.1 §14 "Supervisor is Python".

### Option 3 — Kun ships a thin abstraction + client, backends are pluggable (✅ selected)
**Selected.** `Kun.Sandbox` contains:

- **Abstractions** — `ISandboxProvider`, `ISandboxHandle`, `IProcesses`,
  `IFiles`, and request/response records whose fields mirror the E2B v2
  REST shape one-to-one (camelCase at the JSON boundary, .NET-idiomatic
  PascalCase in code via `JsonPropertyName` on records).
- **Implementations** (pluggable):
  - `InMemorySandboxProvider` — fake for unit tests; no Docker, no network.
  - `SupervisorSandboxProvider` — HTTP client against
    `/v2/sandboxes/*` on the NeuroAgent Supervisor (Phase 1 production path).
  - `E2BCloudSandboxProvider` — skeleton that throws `NotImplementedException`;
    to be filled in when Phase 2+ Mode D is actually scoped.
- **DI** — `services.AddKunSandbox(opts => opts.UseSupervisor(url, cert) | opts.UseE2BCloud(key, team) | opts.UseInMemory())`.

## 5. Decision

**Adopt Option 3.** The framework layer gains a new module:

```
src/Kun.Sandbox/
  Kun.Sandbox.csproj             (IsAotCandidate=true)
  AGENTS.md
  Abstractions/
    ISandboxProvider.cs
    ISandboxHandle.cs
    IProcesses.cs
    IFiles.cs
    SandboxCreateOptions.cs
    ProcessRunOptions.cs
    ProcessResult.cs
    FileEntry.cs
  Implementations/
    InMemorySandboxProvider.cs
    SupervisorSandboxProvider.cs
    E2BCloudSandboxProvider.cs
  Extensions/
    ServiceCollectionExtensions.cs
  Internal/
    SandboxJsonContext.cs        (source-generated JSON for AOT)
```

**The interface contract is "the E2B v2 API in C# records"**:

- `ISandboxProvider.CreateAsync(SandboxCreateOptions, CT)` maps to
  `POST /v2/sandboxes`.
- `ISandboxHandle.Processes.RunAsync(cmd, ProcessRunOptions, CT)` maps
  to `POST /v2/sandboxes/{id}/processes`.
- `ISandboxHandle.Files.ReadAsync/WriteAsync/ListAsync/DeleteAsync`
  map to `GET/POST/GET .../list/DELETE /v2/sandboxes/{id}/files` (with
  `?path=` query parameters per Spec v1.1 §4.5).
- `ISandboxHandle.KillAsync()` maps to
  `DELETE /v2/sandboxes/{id}`.

Record fields carry `[JsonPropertyName]` attributes that emit
**camelCase** at the JSON boundary (matching E2B) while keeping
idiomatic PascalCase inside the .NET code. NeuroAgent extensions
(secret scope, browser, egress, max commands) live under a
`NeuroagentExtension` property on `SandboxCreateOptions` serialised as
the `neuroagent` sub-object — exactly mirroring the spec.

## 6. Consequences

### Positive

- C# business services can directly consume sandboxes through a
  typed, AOT-friendly API without learning HTTP / E2B schemas inline.
- The abstraction is backend-agnostic: swapping
  `UseSupervisor` → `UseE2BCloud` is a one-line change when Mode D is
  scoped.
- Unit tests can use `InMemorySandboxProvider` with no Docker
  dependency.
- The interface contract is the E2B v2 shape, so .NET call sites and
  Python SDK call sites read the same — lower cognitive load for
  engineers crossing stacks.

### Negative / Trade-offs

- `Kun.Sandbox` must track E2B v2 API evolution. Mitigation: monitor
  E2B changelog (same rule as ADR-S01). Breaking changes cascade
  through `Kun.Sandbox` to all consumers; that is intended.
- `Kun.Sandbox` does **not** own a runtime. Any expectation that a
  local `UseInMemory()` provides real isolation is wrong — it is a test
  fake. AGENTS.md and XML docs are explicit about this.
- The Supervisor client path requires S2S JWT + mTLS to the Supervisor.
  Callers must wire `Kun.Security` (or an equivalent S2S token source)
  into the `HttpClient` via a `DelegatingHandler`. Docs show the
  canonical wiring.

### Risks

| Risk | Mitigation |
|------|------------|
| Consumer drifts the record shape away from E2B schema | CI contract test: `SandboxCreateOptions` / `ProcessResult` JSON output diffed against a golden fixture derived from E2B v2 docs; diff > 0 fails the build. |
| `InMemorySandboxProvider` leaks into production wiring | `AddKunSandbox` + `UseInMemory` name signals "test only"; AGENTS.md calls it out; follow-up can add a `KUN_SANDBOX_ALLOW_INMEMORY_IN_PROD=false` guard if abuse appears. |
| Supervisor upgrades a field shape mid-flight | Records use `[JsonPropertyName]` + `JsonIgnoreCondition.WhenWritingNull` so additive changes are backward-compatible; breaking changes require an explicit version bump. |
| E2B Cloud provider is tempting to "finish early" | The stub throws `NotImplementedException` with a clear message. Filling it requires a dedicated task after Mode D is scoped — not a drive-by. |

## 7. Alternatives not taken

- Owning the runtime in .NET (Option 2): rejected; Supervisor is Python
  by design.
- A single provider that branches internally on `BackendKind`: rejected;
  three explicit implementations are clearer and each can carry its own
  dependencies / tests.
- Exposing raw `HttpClient` with helper methods: rejected; would force
  every consumer to re-derive the URL shape and undermine the
  abstraction's reason for existing.

## 8. Validation

- Spec alignment: `SandboxCreateOptions` JSON payload (camelCase,
  `cpuCount`/`memoryMB`/`timeoutMs`/`envs`/`metadata`/`neuroagent.*`)
  matches the request body in Spec v1.1 §4.3 byte-for-byte.
- AOT: CI AOT-publish matrix adds `Kun.Sandbox` and runs
  `dotnet publish -p:PublishAot=true /warnaserror` with zero warnings.
- Tests: `tests/Kun.Sandbox.Tests/` includes ≥ 15 tests (in-memory
  lifecycle, Supervisor request-shape via WireMock.Net, E2B-Cloud stub
  surface, DI options round-trip, camelCase serialisation, parallel
  sandbox isolation).
