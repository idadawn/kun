# Kun Framework — Benchmark Baseline · 2026-04-23

> **Purpose.** Establish performance baselines for the four hot paths
> exercised by `benchmarks/Kun.Benchmarks` so Phase 2+ refactors can be
> measured as a delta, not re-discovered from scratch. Numbers below
> are the Phase 1 anchor; a delta > 25 % against this table on the same
> hardware is expected to be justified in the PR description.

## Methodology

- **BenchmarkDotNet** 0.14.0 with the default `ShortRunJob` (3 warm-up,
  3 measurement iterations). Run via `dotnet run -c Release`.
- Exporters enabled programmatically: `JsonExporter.Default` +
  `MarkdownExporter.GitHub`. Artifacts land under
  `benchmarks/Kun.Benchmarks/BenchmarkDotNet.Artifacts/results/` and are
  gitignored — upload from the CI `Benchmarks` workflow_dispatch run if
  you need a pristine copy.
- `[MemoryDiagnoser]` is applied to every class, so every row reports
  `Mean`, `Allocated`, `Gen0/Gen1/Gen2` collections, and a ratio vs. the
  configured class baseline.
- Redis and S3 are substituted with in-process fakes
  (`MemoryDistributedCache`, `AmazonS3Client` with dummy credentials).
  These baselines therefore capture the **library-local cost** —
  serialization, key hashing, Expression evaluation, HMAC signing —
  not network RTT. A delta against these numbers is a library
  regression; a delta against a real Redis / S3 backend is an infra issue.

## Reproducing

```bash
# Full suite (~4–5 minutes on an 8-core laptop at ShortRunJob)
dotnet run -c Release --project benchmarks/Kun.Benchmarks -- --filter '*'

# Single class
dotnet run -c Release --project benchmarks/Kun.Benchmarks -- --filter '*CachingBenchmarks*'

# CI: trigger the `Benchmarks` workflow_dispatch job from the Actions tab;
# the per-run artifact is uploaded as benchmark-results-<run_id>.
```

## Results

### CachingBenchmarks — Memory vs Distributed-fake

`[Params(10, 100, 1000)] KeyLength` — baseline is `Memory · Set` at the
matching key length.

| Benchmark            | KeyLength |      Mean | Ratio | Allocated | Alloc Ratio |
|----------------------|----------:|----------:|------:|----------:|------------:|
| Memory · Set         |        10 |    139 ns |  1.00 |     216 B |        1.00 |
| Memory · Get         |        10 |     59 ns |  0.43 |     144 B |        0.67 |
| Memory · Remove      |        10 |     60 ns |  0.44 |       0 B |        0.00 |
| Distributed · Set    |        10 |    209 ns |  1.53 |     192 B |        0.89 |
| Distributed · Get    |        10 |    211 ns |  1.54 |     240 B |        1.11 |
| Distributed · Remove |        10 |     81 ns |  0.59 |       0 B |        0.00 |
| Memory · Set         |       100 |    141 ns |  1.00 |     216 B |        1.00 |
| Memory · Get         |       100 |     77 ns |  0.55 |     144 B |        0.67 |
| Memory · Remove      |       100 |     75 ns |  0.53 |       0 B |        0.00 |
| Distributed · Set    |       100 |    252 ns |  1.79 |     192 B |        0.89 |
| Distributed · Get    |       100 |    188 ns |  1.33 |     240 B |        1.11 |
| Distributed · Remove |       100 |     85 ns |  0.61 |       0 B |        0.00 |
| Memory · Set         |      1000 |    489 ns |  1.00 |     216 B |        1.00 |
| Memory · Get         |      1000 |    242 ns |  0.49 |     144 B |        0.67 |
| Memory · Remove      |      1000 |    238 ns |  0.49 |       0 B |        0.00 |
| Distributed · Set    |      1000 |    644 ns |  1.32 |     192 B |        0.89 |
| Distributed · Get    |      1000 |    351 ns |  0.72 |     240 B |        1.11 |
| Distributed · Remove |      1000 |    252 ns |  0.52 |       0 B |        0.00 |

**Observations.**

- Distributed/Memory ratio at KeyLength=10 is ~1.5× — the serializer +
  `IDistributedCache` dispatch tax is dominated by the JSON round-trip
  (`_value = "v"` serialises to 3 bytes UTF-8). At KeyLength=1000 the
  ratio *drops* to ~1.3× because the cache-lookup string-building cost
  is the same for both backends and starts dominating the serialisation
  tax.
- All Set operations allocate 192–216 B per call; Remove is allocation-free
  on both backends. Get on Memory allocates 144 B (the unwrapped
  string value) while Distributed allocates an extra 96 B
  (the byte[] → string conversion in the serializer).

### StorageBenchmarks — Local I/O + S3 presigned URL signing

Baseline is `Local · PutObject 1 KiB`. Class-local ratios below (BDN's
joined summary ratios are computed against the first class baseline in
alphabetic order, so its "Ratio" column must be re-normalised per class).

| Benchmark                   |       Mean | Class Ratio | Allocated |
|-----------------------------|-----------:|------------:|----------:|
| Local · PutObject 1 KiB     | 257 µs     |        1.00 |    96 KB  |
| Local · HeadObject          |  74 µs     |        0.29 |    11 KB  |
| Local · GetObject 1 KiB     |  15 µs     |        0.06 |  1.1 KB   |
| S3 · GetPreSignedURL (PUT)  |  39 µs     |        0.15 |    38 KB  |
| S3 · GetPreSignedURL (GET)  |  38 µs     |        0.15 |    37 KB  |

**Observations.**

- `Local · PutObject` allocates ~96 KB per call — most of it is the
  SHA-256 hasher (`IncrementalHash`) + the `{key}.kun-meta` sidecar
  write. Any refactor that cuts the sidecar format or avoids the
  per-call hasher allocation should show up here.
- `Local · GetObject` is the cheapest path (no hasher, no sidecar
  parse) and mostly measures `File.OpenRead` + `Stream.CopyTo`.
- S3 presigned-URL generation is ~40 µs of CPU-bound HMAC-SHA256
  signing (plus the 38 KB of AWS SDK request-object allocations).
  This is the cost a service pays per presigned URL handed out to
  a client; at ~25 k URLs/sec per core on this box, CPU is not the
  bottleneck for normal throughput.

### AuditInterceptorBenchmarks — SaveChanges overhead

Baseline is `SaveChanges · no interceptor`. **Warning — these two rows
have very high variance** (Error = ~125 % of Mean for the baseline,
~295 % of Mean with the interceptor). The delta below is directional
only and is tracked as a known caveat; for a tight regression budget
here you need `--job default` on a quiet machine.

| Benchmark                                     |      Mean |   Allocated |
|-----------------------------------------------|----------:|------------:|
| SaveChanges · no interceptor                  |  4.1 ms   |   5.5 MB    |
| SaveChanges · with AuditSaveChangesInterceptor |  1.0 ms   |   1.4 MB    |

**Observations & caveat.**

- The "with interceptor" row measuring *faster* than the baseline is
  counter-intuitive and driven by EF Core InMemory's first-call
  model-compile tax landing on whichever DbContext BDN runs first.
  Both contexts are constructed in `[GlobalSetup]` but neither is
  warmed up — the alphabetically-first benchmark (`SaveChanges_no_interceptor`)
  absorbs the compile cost on its first invocation and poisons the
  baseline. A follow-up B3 refinement should call
  `await ctx.SaveChangesAsync(); ctx.ChangeTracker.Clear();` once per
  context in `[GlobalSetup]` so both sides are measured at steady state.
- Even with that caveat, the absolute **allocated** numbers are
  meaningful: the interceptor path allocates ~1.4 MB per
  SaveChangesAsync, most of which is the `Utf8JsonWriter` rental +
  `AuditLog` objects. A refactor that cuts this without functional
  regression would be a strong Phase 2 win.

### MultiTenancyQueryFilterBenchmarks — Query filter overhead

`[Params(100, 1000)] RowCount` — baseline is `Query · no tenant
filter (manual Where)` at the matching row count.

| Benchmark                                  | RowCount |       Mean | Ratio | Allocated | Alloc Ratio |
|--------------------------------------------|---------:|-----------:|------:|----------:|------------:|
| Query · no tenant filter (manual Where)    |      100 |   36.4 µs  |  1.00 |   53 KB   |        1.00 |
| Query · Kun tenant filter (HasQueryFilter) |      100 |   29.4 µs  |  0.81 |   51 KB   |        0.95 |
| Query · no tenant filter (manual Where)    |     1000 |  267.8 µs  |  1.00 |  471 KB   |        1.00 |
| Query · Kun tenant filter (HasQueryFilter) |     1000 |  252.7 µs  |  0.95 |  468 KB   |        0.99 |

**Observations.**

- The Kun tenant filter is ~5–20 % *faster* than the equivalent manual
  `Where(x => x.TenantId == c)` on EF InMemory at these row counts.
  On InMemory the Expression tree built by
  `ApplyKunMultiTenantFilters` gets cached once at model creation,
  while the manual `Where` builds a fresh closure-capturing expression
  per invocation — that's the allocated-delta we see (~3 KB / ~3 KB
  less per query for the filter path).
- On a real relational backend (PostgreSQL), the EF Core SQL translator
  would likely erase this delta — the SQL plan is identical. Take the
  numbers above as a library-local baseline, not an endorsement of one
  pattern over the other at the SQL layer.

## Methodology notes & honesty disclaimers

- **ShortRunJob is noisy.** The numbers above survive day-to-day
  regression detection at the 25 % band. For release-grade numbers,
  rerun at `--job default` on a dedicated machine and accept the
  longer wall-clock (~30 – 60 minutes for the full suite).
- **BDN `ConfigOptions.JoinSummary` confuses ratios across classes.**
  The `Ratio` column in the BDN console summary normalises against
  the first-alphabetic class's baseline, which is why the Storage /
  Audit / MultiTenancy rows in the raw output have ratios < 1 even
  though they have their own `[Baseline=true]`. The tables above
  re-compute class-local ratios manually.
- **In-process "Redis" is not Redis.** `MemoryDistributedCache` omits
  TCP framing, roundtrip latency, and server-side cost. The baseline
  is sensitive to library regressions (serializer allocations,
  `KeyPrefixer` string builder, options validation) — not network
  performance. Real-Redis benchmarks belong in a separate Testcontainers
  suite not tracked here.
- **AWS SDK presigned-URL signing** runs fully offline in the SDK;
  the `AmazonS3Client` here is constructed with dummy credentials and
  a bogus endpoint so no DNS or TCP happens. Numbers here match what
  a service would spend in CPU to issue N presigned URLs per second;
  add your provisioning's network egress on top for real throughput.
