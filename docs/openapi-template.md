# OpenAPI pipeline template

> Source-gen-friendly, AOT-compatible OpenAPI wiring for Kun services built
> on Minimal API + `Kun.AspNetCore.MapCommand` / `MapQuery`.
>
> Last updated: 2026-04-22.

## What .NET 10 ships

`Microsoft.AspNetCore.OpenApi` exposes `/openapi/v1.json` via:

```csharp
builder.Services.AddOpenApi();   // service registration
// ...
app.MapOpenApi();                // endpoint mapping
```

The document is generated by the built-in `Microsoft.AspNetCore.OpenApi`
provider. Unlike Swashbuckle, it goes through the same endpoint metadata
pipeline ASP.NET uses at runtime, so what you see in the document matches
what ships on the wire — including anything `Results.Problem`, `Produces`,
`Accepts` or `WithTags` on your `Map*` calls contribute.

## Recommended wiring for a Kun service

```csharp
var builder = WebApplication.CreateBuilder(args);

// Core Kun services (mediator, validation, EF, …) first.
builder.Services.AddKunAspNetCore();
builder.Services.AddKunMediator(/* handlers */);

// OpenAPI last — it reads endpoint metadata at request time, so order
// doesn't strictly matter, but grouping it near other surface-area
// registrations helps future readers find the toggle.
builder.Services.AddOpenApi();

var app = builder.Build();
app.UseExceptionHandler();

// Gate the endpoint on Development by default so production deployments
// don't silently ship the document. Flip this on explicitly for staging
// or for consumer-onboarding APIs.
if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
}

app.MapCommand<CreateProductCommand, Guid>(
    "/products",
    CatalogJsonContext.Default.CreateProductCommand,
    CatalogJsonContext.Default.Guid);

app.Run();
```

## Why it's AOT-friendly

- `AddOpenApi()` + `MapOpenApi()` read metadata from already-registered
  endpoints; they don't scan assemblies or reflect over user types beyond
  what ASP.NET itself does. That keeps the AOT analyzer happy.
- Request/response shapes that Kun routes send through `MapCommand` /
  `MapQuery` flow through `System.Text.Json` using **source-generated**
  `JsonTypeInfo` (the `CatalogJsonContext.Default.*` accessors). OpenAPI
  reads schemas from the compile-time metadata those `JsonTypeInfo`
  instances carry, which means property names and nullability appear in
  the document without runtime reflection.
- There is no `GenerateApiDescriptor`-style reflection pass; the document
  is lazily built on first request.

## Gating the endpoint

The document exposes internal type names, parameter shapes, and sometimes
comments. Default posture:

| Environment | Exposed? | Rationale |
|---|---|---|
| Development | yes | Local iteration + onboarding |
| Staging | **opt-in** via config | Partner preview, QA handoff |
| Production | **no** unless you run a public-SDK programme | Minimise attack surface |

A typical config-driven gate:

```csharp
var exposeOpenApi = builder.Environment.IsDevelopment()
    || builder.Configuration.GetValue<bool>("OpenApi:Expose");

// ...

if (exposeOpenApi)
{
    app.MapOpenApi();
}
```

Then `appsettings.Staging.json` turns it on explicitly:

```json
{ "OpenApi": { "Expose": true } }
```

## Consuming the document

### Local smoke test

```bash
# In one terminal
dotnet run --project samples/Kun.Sample.Catalog

# In another
curl -s http://localhost:<port>/openapi/v1.json | jq '.paths | keys'
```

You should see every route you registered, including the ones that
`Kun.AspNetCore.MapCommand` / `MapQuery` expand to.

### CI smoke test

Bundle the check into your sample integration suite so regressions surface
before release:

```csharp
[Fact]
public async Task OpenApi_Document_Is_Served_When_Development()
{
    await using var factory = new WebApplicationFactory<Program>()
        .WithWebHostBuilder(b => b.UseEnvironment("Development"));
    using var client = factory.CreateClient();

    var response = await client.GetAsync("/openapi/v1.json");
    response.EnsureSuccessStatusCode();

    using var doc = JsonDocument.Parse(
        await response.Content.ReadAsStringAsync());
    Assert.True(doc.RootElement.GetProperty("paths")
        .EnumerateObject().Any(),
        "OpenAPI document must list at least one path");
}
```

### Client generation

Feed the document to any OpenAPI-aware generator — the stock .NET 10
document emits draft-ish OAS 3.1, which modern Kiota / NSwag / openapi-ts
handle cleanly. Run the generator once per release; do not check the
generated client into `kun` itself — consumer repos own their client
artifacts.

## What NOT to do

- Don't add `Swashbuckle.AspNetCore`. It predates the built-in provider and
  pulls in a reflection-based pipeline that defeats the AOT analyzer.
- Don't enable `MapOpenApi()` unconditionally in production unless the
  service is part of a deliberate public SDK programme.
- Don't rely on XML comments for schema descriptions in AOT services — the
  XML-doc pipeline isn't source-gen-backed. If you need rich descriptions,
  add them via `[Description(...)]` attributes on the DTO properties
  instead.
- Don't check the generated `openapi.json` into git alongside the service.
  The endpoint is the source of truth; drift between a committed snapshot
  and live behaviour is a common bug source.
